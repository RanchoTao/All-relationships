## 0. 背景与方向（必须理解）

AllRelationships 是一座"人类关系博物馆"：479 个关系名称与场景、17 个目录分类，静态站（Next.js 16 / React 19 / Tailwind 4 / Zod，GitHub Pages）。它未来是 Dearwithme（关系意向与双向撮合）的知识层。

**本阶段的产品方向已经确定：**

1. **网站要先完善成一座"内容完整"的馆。** 479 个词条每一个都要有详细、可读、互不重复的说明卡。现在只有 60 张卡，而且这 60 张卡是 `scripts/author-knowledge.mjs` 用模板从约 11 个短字段拼接出来的：`interactions` 重复 `scenarios`，`conflicts` 重复 `boundaries`，`deepDive` 各段开头原样复制 `definition`、`needs`、`participants`。**这 60 张也要重写。**
2. **偏好探索（/explore）的目标改变：** 不再暗示"测出你真正想要什么关系"。研究表明自述的理想偏好难以预测真实吸引（Eastwick & Finkel, 2008; Eastwick et al., 2014 meta-analysis）。问卷的新目标是：**帮用户把"当下愿意接受的关系安排"和"底线"说清楚**，输出一份可修改的"关系菜单"（我想要／可以谈／不要），每一项链接到 Wiki 词条解释。匹配的逻辑是"说清条件 → 排除结构冲突 → 低成本尝试 → 反馈修正"，不是读心。
3. Wiki 是问卷结果的"注释层"。所以**写卡优先级跟随问卷**：问卷会推荐、会提及的词条先写。

## 1. 不可违反的约束

- **不修改** `data/raw/` 与 `data/draft/AllRelationships_479_catalog_v0.2.json`；`data/knowledge/history-lock.json` 的历史哈希校验必须继续通过。新内容只写在 `data/knowledge/` 的新层。
- **稳定 ID 不变、不删除词条。** 近义或重复词条用显式 `aliasOf` / `seeAlso` 关系处理，不要合并删除，也不要为凑数写两张几乎一样的卡。
- **不编造来源。** 每个 `sources` 记录必须是真实存在、你实际打开过的页面，记录 URL、定位（章节／段落）、支持的具体命题、局限。打不开或只看到摘要就如实标 `abstract_only` / `metadata_only`。没有合适来源的卡可以零来源，但不要挂"概览 URL"凑数。
- **不伪造审核。** `independentReview` 只能由真人改为 `reviewed`，并填 `humanReviewer`、日期、修改理由。你（AI）只能把状态设为 `ai_drafted` 或 `ai_self_checked`。
- **风险条目**（强迫、剥削、欺凌、骚扰、权力滥用等）只作描述与求助指引，不进入推荐，不写"如何建立"。
- **涉及未成年人的条目**只写家庭、教育、照护等非亲密语境，绝不出现在亲密／约会推荐中。
- **法律相关表述**必须写明法域与适用条件，或者不写。
- **运行时不调用任何付费 API、不收集用户数据、不加分析脚本或远程字体。** 问卷答案只在浏览器本地。
- **UI 风格不要大改。** 设计重做之后由 Claude 负责。你可以新增必要的页面结构与组件，但沿用 `globals.css` 里已有的 token（`--font-serif`、`--green`、`.badge-*` 等）和现有的视觉语言。
- 每个 PR 必须通过：`npm run validate:data && npm run test:unit && npm run typecheck && npm run lint && npm run build:pages && npm run test:pages`，三个视口的 axe 无障碍检查为 0 违规。

## 2. 阶段 A：内容系统重构（一个 PR）

目标：从"模板拼接"改为"逐卡手写、逐卡一个文件"，并用校验阻止模板化内容。

1. **新的存储结构：** `data/knowledge/cards/<ID>.json`，每张卡一个文件。`cards.json` 改为构建时由这些文件聚合生成（或直接由 `knowledge.ts` 读取目录）。`author-knowledge.mjs` 做一次迁移后退役（保留在 git 历史中即可）。
2. **Schema v0.4**（Zod，放 `src/lib/schema.ts` 或新的 `knowledge-schema.ts`），在现有字段基础上：
   - `depth`: `"deep" | "standard" | "brief"`。
     - `deep`：核心原型和问卷高频目标，正文合计约 1500–3000 字；
     - `standard`：大多数词条，约 600–1200 字；
     - `brief`：生命周期状态、极窄的情境标签、风险条目，约 250–500 字，但字段齐全。
   - `summary`：一句话（≤ 60 字），用于卡片墙与问卷结果。**不同于 `definition`。**
   - `definition`：2–4 句的工作定义。
   - `whatItLooksLike`：2–4 个**具体**、彼此不同的虚构情境，每个写清谁、做什么、频率／场合。
   - `negotiables`：这段关系里**通常需要说清**的议题清单。每项包含 `topic`（如"联系频率""是否同住""费用分担""排他范围""公开程度""退出方式"）、`options`（2–4 个常见安排）、`dimension`（对应问卷维度 id）。**这是问卷"关系菜单"的数据来源，最重要。**
   - `commonDealbreakers`：此关系里常见的硬冲突（结构性，不是性格）。
   - `misconceptions`、`distinctions`（≥ 2 个相邻词条，含 `targetId` 与差异说明）、`changes`（如何开始、如何演变、如何结束）。
   - `relatedIds`、`aliasOf`（可选）、`seeAlso`。
   - `evidence`：沿用现有结构，`independentReview` 枚举改为 `pending | ai_drafted | ai_self_checked | reviewed`。
   - `facets`：沿用现有八个属性键，只填有依据的值。
   - 免责说明只在卡片层面写一次（`evidence.note`），不要在每个字段里重复"由当事人决定""不代表普遍"这类句子。
3. **新增内容质量校验**（写进 `scripts/validate-knowledge.ts` 并在 CI 中失败即阻断）：
   - 同一张卡内，任意两个字段之间不得有长度 ≥ 20 字的相同子串；
   - 跨卡"样板句"：同一句话（≥ 15 字）在超过 5 张卡中出现即失败（允许列入白名单的极少数固定说明）；
   - 每个 depth 的最小字数和字段数量；
   - `negotiables` 至少 3 项（`brief` 至少 1 项，风险条目可为 0）；
   - `distinctions` 引用的 ID 存在且不指向自己；`sourceIds` 存在；
   - 覆盖报告输出：各 depth 数量、有来源的卡数、`ai_self_checked` 数、`reviewed` 数、尚缺的 ID 列表。
4. 去掉 `validate-knowledge.ts` 里写死的 `60` / `20` 断言，改为基于目录的动态校验。
5. 前端：详情页按新字段渲染（`negotiables` 用清晰的表格或清单，`whatItLooksLike` 用情境卡），卡片墙用 `summary`。保持现有布局，不做大的视觉改动。

## 4. 阶段 C：补全其余 419 张卡（多个 PR，每批 25–40 张）

**优先级顺序：**

1. 问卷当前和 v0.2 会推荐或提及的所有目标词条（从 `src/lib/assessment.ts` 的模板与推荐逻辑中提取完整 ID 列表，写进 `docs/handoff/priority-ids.md`）；
2. 恋爱与约会（A01–A03）、友谊与活动伙伴（A04–A05）、共同生活（含室友、合住）；
3. 学习、研究、职业、合作类；
4. 家庭、照护、社区、制度角色；
5. 生命周期状态与风险条目（多数为 `brief`）。

**每批 PR 要求：**

- PR 描述列出本批 ID、各 depth 数量、新增来源、遇到的分类问题（例如某条其实是另一条的别名、某条分类错位）。
- 遇到近义词条：短的那张写 `brief` 并设置 `aliasOf` 或 `seeAlso`，正文说明二者的差别或重合，不要复制主卡内容。
- 写作风格：中文，书面但好读。具体胜过抽象，例子要有生活质感。可以说"常见的情况是……"，但不要编造比例或发生率。少用"可能""通常"一类空洞的套话，需要表达不确定时说清楚是哪里不确定。
- 同一批里先写一张"样板卡"放在 PR 描述最上方，方便抽查语气。
- **每批结束跑一次内容质量校验**，并在 PR 中贴出覆盖报告的增量。

## 6. 阶段 E：偏好探索 v0.2（一个 PR，在阶段 B 之后、可与阶段 C 并行）

保留现有 `/explore` 的路由与隐私原则（只在本页内存计算、可跳过／不确定／不适用／修改／否认）。变更如下：

1. **重写文案定位：** 页面与结果中去掉任何"测出真实需求／真正想要"的暗示，改为"把你现在愿意的安排和底线说清楚"。在 `/explore/method` 中引用 Eastwick & Finkel (2008) 与 Eastwick et al. (2014)，简要说明为何不做诊断。
2. **题目结构改成三段：**
   - **方向**（保留现有的需求入口：友谊、活动、学习研究、居住、社区、成年人恋爱等）；
   - **安排**：针对选定方向，从相关卡片的 `negotiables` 中取议题，每题给出 2–4 个选项，加上"可以谈""不确定"；
   - **底线**：明确问"哪些是绝对不能接受的"（多选），来自 `commonDealbreakers`。
3. **结果改为"关系菜单"：** 三列——我想要／可以谈／不要。每一项可点开对应词条。顶部列出 3–5 个"可能贴近的关系名称"，**仅作为阅读入口**，并注明理由（来自哪几题的回答）。用户可以在结果页直接修改任何一项，修改立即生效。
4. **双人对照模式（无后端）：** 结果可导出为一个 URL 片段（`#` 之后，base64url 编码的紧凑 JSON，含 schema 版本号），不经过服务器。另一人打开链接、填写自己的问卷后，页面显示"一致／可协商／冲突"三栏。要求：
   - 链接页明确说明"内容在链接中，谁拿到链接都能看到"，由用户决定是否分享；
   - 涉及亲密、性相关的议题，默认不包含在分享链接里，需用户逐项勾选才包含；
   - 解析失败或版本不符时友好提示，不崩溃。
5. **自我反馈：** 结果页对每个推荐项提供"像我／不像我"，只存在当前页面内存（可选：用户主动点击"在本设备保存"才写 `localStorage`，并提供一键清除）。
6. 题库扩展后，单次问卷长度仍控制在约 8–15 题；要有"跳到结果"的出口。
7. 更新 `tests/assessment.test.ts` 与 `tests/browser/explore.spec.ts`：覆盖分支、底线、修改结果、分享链接编码／解码（含篡改与版本不符）。
